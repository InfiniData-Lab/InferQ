# Out-of-Core RDBMS Quantum Simulation: Experimental Report

SIGMOD revision E1 / R1.O1 / R2.Q2.

## 1. Research question

Quantum circuit simulators based on dense statevectors (notably Qiskit
Aer) allocate memory proportional to `2^N · 16 B`, and abort when the
allocation fails. There is no graceful degradation: a circuit with one
extra qubit doubles memory demand, and once the demand exceeds available
RAM, simulation is impossible. RDBMS-based quantum simulation, in
contrast, expresses the simulation as a relational query whose
intermediates can be spilled to disk when memory pressure exceeds the
budget — a property inherited from the engine's general-purpose
out-of-core machinery (hash spill, sort spill, temporary tablespaces).
The hypothesis is that RDBMS-based simulation succeeds under memory
constraints where Aer fails outright, and that for sufficiently large
circuits this success is the *only* way to obtain a result on
commodity hardware.

The experiment is designed to substantiate three claims:

- **C1 (capability gap).** There is a regime — circuits ≥ 31 qubits
  under any of the memory caps we test — where every Aer simulation
  method fails and at least one RDBMS engine succeeds.
- **C2 (graceful degradation).** Across the cap sweep, Aer's success
  rate cliff-drops at the cap that crosses its statevector threshold,
  whereas RDBMS engines degrade smoothly: as the cap tightens, wall
  time increases and spill bytes increase, but the run still completes.
- **C3 (paid in time, not failure).** When RDBMS engines spill, the
  cost is wall-clock time, not result correctness. A spilled run
  produces the same final amplitudes as an in-memory run of the same
  query.

Claim C3 is verified out-of-band by comparing the spilled query's
result against an unconstrained baseline; it is not the focus of the
memory-cap sweep itself.

## 2. Engines under test

We compare four engines, all of which produce a final amplitude vector
for the input circuit:

| Engine | Version | Mode |
|---|---|---|
| Qiskit Aer | 0.17.0 | statevector, matrix_product_state, density_matrix, stabilizer, automatic |
| PostgreSQL | 16 (tuned) | server with custom postgresql.conf |
| DuckDB | 1.1.3 | embedded (in-process) |
| SQLite | system (3.x) | embedded (in-process) |

The five Aer methods are run separately because they have very
different memory profiles: `statevector` is the dense baseline,
`matrix_product_state` and `density_matrix` are tensor-network /
mixed-state alternatives that may fit when statevector cannot, and
`stabilizer` succeeds only on Clifford circuits (we record its
"invalid parameters" responses on non-Clifford inputs as expected).

The three RDBMS engines all execute the same SQL representation of
the circuit, generated by `InfiniQuantumSim` (the relational tensor
contractor that this paper introduces). PostgreSQL is included as the
representative server-class engine; DuckDB as an embedded analytical
engine; SQLite as an embedded transactional engine. Together they
span the range of architectures a practitioner is likely to consider.

## 3. Workload and circuit selection

### 3.1 Source corpus

The InferQ metadata corpus (≈ 200 k circuits) is filtered to the
subset for which at least one prior unconstrained RDBMS run produced
a result. This guarantees that the SQL plan is known to be valid for
the engines we test, and that any failure under a memory cap reflects
the cap rather than an unrelated SQL-generation issue.

### 3.2 Stratified sampling by qubit count

Circuits are stratified into five bins on qubit count:

| Bin | Qubits | Aer statevector size | Story |
|---|---|---|---|
| `B0_trivial` | < 25 | ≤ 512 MB | Baseline: every engine succeeds at every cap |
| `B1_aer_ok_all_caps` | 25–27 | 0.5–2 GB | Aer fits at every cap; RDBMS may spill at 4 GB |
| `B2_aer_fails_at_4` | 28–29 | 4–8 GB | Aer OOMs at cap=4; RDBMS must spill |
| `B3_aer_fails_at_8` | 30 | 16 GB | Aer OOMs at caps 4 and 8; RDBMS spills |
| `B4_aer_impossible` | ≥ 31 | ≥ 32 GB | **Headline:** Aer OOMs everywhere; RDBMS succeeds |

We bin on qubit count rather than on the prior tracemalloc-based
peak-memory figures stored in the corpus metadata, because tracemalloc
sees only the Python heap and underestimates true footprint by 10–100×;
qubit count directly predicts Aer's statevector size and is the
cleanest OOM-threshold proxy available.

Within each bin we sample 20 circuits with sub-stratification by
qubit count (so a single qubit value cannot dominate a bin). Sampling
is hardness-weighted: within each qubit bucket we draw uniformly from
the top half by prior unconstrained RDBMS wall time. The full sample
is 73 circuits (B4 is smaller because few corpus circuits exceed 30
qubits). A pilot configuration (5 circuits per bin, 25 total) is
provided for fast smoke runs.

### 3.3 SQL generation

For each circuit, the worker transpiles the Qiskit circuit to the
basis `{u, cx, id, rz, sx, x}` (optimization level 2) and feeds it to
`InfiniQuantumSim`'s `to_query()`, which performs `opt_einsum`
path-finding and emits a single SQL string. Path-finding has no
internal timeout and can hang on certain circuit structures, so
generation runs in a daemon thread bounded by the per-run timeout
(1800 s). Generation is *not* counted in `wall_time_s`; only engine
execution is timed.

## 4. Hardware and software environment

All experiments run on a single Linux host:

- **Machine.** Alienware Aurora R13 — Intel i9-12900KF (16 c / 24 t),
  64 GB DDR5, Micron 3400 NVMe (2 TB) on ext4.
- **Operating system.** Ubuntu 22.04, kernel 5.15. Hybrid cgroup v1+v2
  configuration: v1 controllers for memory, blkio, cpu, etc., and a
  v2 unified hierarchy for tracking only.
- **Docker.** Engine ≥ 24.0 with the `cgroupfs` cgroup driver. Per
  container, `--memory`, `--memory-swap`, and `--memory-swappiness`
  control cgroup v1 memory and swap accounting.

Two Docker images are built once per experiment campaign:

- `inferq-ooc-postgres:12.22` — PostgreSQL 12.22 with a templated
  `postgresql.conf` whose `shared_buffers`, `effective_cache_size`,
  and `temp_file_limit` are scaled to `CAP_GB` at container start.
- `inferq-ooc-worker:latest` — `python:3.11-slim` with Qiskit, Aer,
  DuckDB, psycopg2, NumPy, SciPy, opt-einsum, and python-dotenv. The
  repo and `OOC_TMP_ROOT` are bind-mounted at runtime.

## 5. Memory enforcement

Every engine runs inside a Docker container with the same enforcement
contract:

```
docker run \
    --memory <cap>g --memory-swap <cap>g --memory-swappiness 0 \
    --network host --cgroupns host \
    -v /sys/fs/cgroup:/sys/fs/cgroup:ro \
    -v /sys/fs/cgroup/memory:/sys/fs/cgroup/memory:ro \
    -v /sys/fs/cgroup/blkio:/sys/fs/cgroup/blkio:ro \
    -v /sys/fs/cgroup/unified:/sys/fs/cgroup/unified:ro \
    -v <REPO>:<REPO>:ro \
    -v <OOC_TMP_ROOT>:<OOC_TMP_ROOT> \
    ...
```

`--memory-swap=cap` (equal to `--memory`) yields an effective swap
budget of zero: the kernel will OOM-kill the container before
swapping. `--memory-swappiness=0` forbids the kernel from preempting
to swap even if a global swapfile is configured. As a sentinel, every
run records `cgroup_swap_peak_bytes`, computed as
`memory.memsw.max_usage_in_bytes − memory.max_usage_in_bytes`; any
non-zero value indicates a configuration error and the run is
discarded.

For PostgreSQL the cap is on the postgres-server container; the
worker runs in a *separate* container with a generous 60 GB cap
(it executes only `psycopg2` + `EXPLAIN`). The two containers
communicate over `host` networking on TCP/54320. For DuckDB, SQLite,
and Aer there is one worker container per triple, and the cap is on
that container.

We chose Docker over `systemd-run --user --scope` after preliminary
experiments showed that the latter does not reliably enforce
`MemoryMax` on Linux hosts where the user session lacks v1 memory
controller delegation — a common configuration on Ubuntu 22.04
hybrid setups. Docker, in contrast, creates per-container cgroups
unconditionally; the same enforcement and accounting machinery used
for the postgres container is now used for every engine, giving a
single defensible enforcement story.

Aer additionally receives an internal hint via
`AerSimulator(max_memory_mb = cap_gb · 1024 − 512)` so that it raises
`InsufficientMemoryError` cleanly before the kernel intervenes; this
distinguishes `oom_internal` (engine self-aborted) from `oom_kill`
(rc=137, kernel OOM-killer) in our status taxonomy.

## 6. Run protocol

### 6.1 Sweep structure

For every (circuit, cap, engine) triple — and for Aer also every
method — the orchestrator:

1. Starts the relevant Postgres container if applicable.
2. Drops the host OS page cache (`sync && echo 3 > drop_caches`)
   so subsequent reads of spilled or data files are cold.
3. Launches a worker container with the cap enforced by Docker.
4. Waits for the worker to exit; reads its JSON output and the
   container's cgroup counters.
5. Removes the worker (and postgres) container.

The run proceeds sequentially over `(circuit, cap, engine, method)`
in nested-loop order. Concurrency between triples would contaminate
the page cache and cgroup-IO accounting on the shared host filesystem,
so it is intentionally avoided.

### 6.2 Repetitions

Each triple records one **warmup** run (discarded) followed by three
**timed** runs. The warmup run absorbs Python import and JIT costs
and primes the engine's internal caches; the three timed runs are the
unit of analysis for `wall_time_s`. cgroup counters and worker peaks
are recorded for the entire subprocess (warmup + timed combined).

### 6.3 Timeouts

Per-run timeout is 1800 s (30 min). For DuckDB it is enforced via
`con.interrupt()` after a wall-clock deadline; for SQLite via
`con.interrupt()` from a watchdog thread; for PostgreSQL via
`SET statement_timeout`. The total per-engine budget is
`(n_runs + warmup + 2) · timeout`, after which the orchestrator force-
kills the container.

### 6.4 Early abort

For Aer, a triple aborts after the first non-warmup run that returns
`oom_internal`. There is no value in retrying once the engine has
declared the configuration infeasible — the circuit and cap are
fixed, and retries would only consume budget. This is reflected in
the CSV by the absence of `run_idx` 1 and 2 for those triples.

### 6.5 Page cache flushing

The host OS page cache is flushed between every triple. Without this,
later runs of the same circuit would read previously spilled files
(or the postgres data files) directly from RAM, understating the
true I/O cost of out-of-core execution. Flushing requires a NOPASSWD
sudoers entry for `tee /proc/sys/vm/drop_caches`.

### 6.6 Temporary file location

`OOC_TMP_ROOT` is set to a directory on the NVMe (`/data/inferq_ooc`),
not the system `/tmp` (which on most Linux distributions is `tmpfs`,
i.e. RAM-backed). This is critical: spill writes to a `tmpfs` would
count against the cgroup memory cap and would not appear in the
`blkio` I/O counters, breaking both the enforcement story and the
spill measurement. The orchestrator verifies the mount type at
startup (`findmnt -no FSTYPE -T <path>`) and aborts if it lands on
`tmpfs` or `ramfs`.

## 7. Metrics

Each `(circuit, cap, engine, method, run_idx)` row in the CSV
contains:

### 7.1 Performance

- `wall_time_s` — `time.perf_counter()` deltas around the engine call.
  For PostgreSQL this is the `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`
  statement; for DuckDB / SQLite it is `execute() + fetchall()`; for
  Aer it is `backend.run(...) + job.result()`. The metric does **not**
  include SQL generation, container startup, or page-cache flushing.

### 7.2 Memory

- `cgroup_mem_peak_bytes` — high-water mark of resident memory for
  the engine's cgroup over the lifetime of the worker container. We
  record three independent observations and take their maximum:
  - **In-container self-report**: the worker, just before exit, reads
    `memory.max_usage_in_bytes` from `/sys/fs/cgroup/memory/<rel>`.
  - **In-container polling sampler**: a daemon thread polls
    `memory.usage_in_bytes` (or `memory.current` on v2-active hosts)
    every 100 ms throughout the run and records the maximum sample.
    This is robust on kernels that lack `memory.peak` (< 5.19) and
    serves as a cross-check on the kernel-reported peak.
  - **Host-side read**: the orchestrator reads
    `memory.max_usage_in_bytes` from the container's cgroup
    directory after the worker process exits but before the
    container is removed.
- `cgroup_swap_peak_bytes` — `memory.memsw.max_usage_in_bytes −
  memory.max_usage_in_bytes`. Configuration sentinel; expected zero
  for every row.
- `tracemalloc_peak_bytes` — Python-heap peak; informational only,
  excludes engine-internal allocations (DuckDB / Postgres / Aer all
  allocate primarily in C/C++).
- `proc_vm_peak_bytes` — `VmPeak` from `/proc/self/status`; includes
  memory-mapped files and is therefore loose. Informational.

### 7.3 Disk I/O

- `proc_io_read_bytes` / `proc_io_write_bytes` — per-run physical
  I/O deltas from `/proc/self/io`, measured around the query
  execution window. For embedded engines (DuckDB and SQLite) the
  write delta is the primary spill/workspace proxy because it is
  per-run and includes writes to on-disk database files, temp files,
  journals, and other engine workspace. It is intentionally reported
  as a **proxy**, not exact spill volume.
- `spill_proxy_bytes` — the analysis-facing spill metric. For
  PostgreSQL it is exact temp bytes written from `EXPLAIN`; for
  DuckDB and SQLite it is `proc_io_write_bytes`. The companion
  `spill_metric_kind` column records the source used.
- `cgroup_io_read_bytes` / `cgroup_io_write_bytes` — cumulative bytes
  read from and written to block devices by the cgroup. On hybrid
  hosts these are read from the v1 `blkio.io_service_bytes` file
  (Read + Write entries summed); on unified hosts from
  `io.stat`. They include all I/O (data files, temp spill, WAL),
  so they are a coarse container-lifetime cross-check, not a
  per-run spill metric.
- `dbms_temp_bytes_written` / `dbms_temp_bytes_read` — engine temp
  accounting where available:
  - **PostgreSQL.** Recursively summed `"Temp Written Blocks"` and
    `"Temp Read Blocks"` from the `EXPLAIN (ANALYZE, BUFFERS,
    FORMAT JSON)` plan tree, multiplied by 8192 (Postgres block size).
  - **DuckDB.** Summed `temporary_storage_bytes`, `spilled_bytes`,
    `bytes_spilled_to_disk` fields across the profiling JSON written
    to `<OOC_TMP_ROOT>/duckdb_<pid>_<run>/profile.json`. DuckDB's
    profile schema varies by version, so this field is diagnostic;
    use `spill_proxy_bytes` for summaries.
  - **SQLite.** No query-level temp-byte counter is exposed through
    Python's stdlib wrapper. New runs leave `dbms_temp_bytes_written`
    empty for SQLite and use `spill_proxy_bytes` instead.
  - **Aer.** Always zero (no spill concept).

Use `spill_proxy_bytes` for plots and tables. Do not describe DuckDB
or SQLite values as exact spill bytes; describe them as process write
volume or spill/workspace proxy. The cgroup I/O counter is retained as
a sanity test that the temp directory genuinely lives on a block
device and that the container is doing physical I/O.

### 7.4 Status taxonomy

| Status | Meaning |
|---|---|
| `success` | Engine returned a result within the timeout |
| `oom_internal` | Engine raised an OOM cleanly (Aer `InsufficientMemoryError`, DuckDB `OutOfMemoryException`) |
| `oom_kill` | Worker process killed by kernel OOM killer (rc=137) |
| `timeout` | Run exceeded the per-run timeout |
| `error` | Any other failure (wrong method, connection refused, etc.) |
| `pg_startup_failed` | Postgres container did not become ready within 60 s |
| `query_gen_timeout` | SQL generation exceeded the wall-clock deadline |

`oom_internal` is the most informative outcome for the paper: the
engine recognised the constraint and terminated cleanly, providing
a *causal* attribution of failure to the memory cap rather than to
an external signal.

## 8. Reproducibility

The complete experiment is reproducible from the contents of this
repository at the commit referenced in the paper, given:

- A Linux host with Docker installed (cgroup mode irrelevant; the
  Docker daemon abstracts it).
- An NVMe-backed mount for `OOC_TMP_ROOT` (≥ 50 GB free).
- A NOPASSWD sudoers entry for `tee /proc/sys/vm/drop_caches`.
- The two Docker images, built via `./experiments/ooc/docker/build.sh`.

Random seeds for stratified sampling are fixed (`seed = 42`); the
manifest written to `data/ooc/circuits.jsonl` therefore selects the
same 73 circuits on every run. The CSV output is append-only; the
orchestrator's `--resume` mode skips triples already recorded, and
`--rerun-statuses` re-runs rows with a given status (e.g. `error`,
`timeout`) without affecting other rows.

Image and engine version pins are recorded explicitly:
`postgres:12.22`, `duckdb==1.1.3`, `qiskit-aer==0.17.0`, `qiskit==2.0.1`,
`numpy==2.2.5`, `scipy==1.15.3`, `opt-einsum==3.3.0`,
`python-dotenv==1.1.0`. The full container manifest, including SHAs,
is reproducible by `docker image inspect inferq-ooc-worker:latest`.
