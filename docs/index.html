Getting started

What InferQ is

InferQ exists to answer a question that needs a large, well-labelled corpus to answer at all: what does it cost to simulate a given quantum circuit, and can that cost be predicted from the circuit's structure? Answering it requires thousands of circuits, each annotated with structural measurements and with the observed cost of running it several different ways. InferQ is the machine that produces that corpus.

The distinctive part is the second simulation path. Alongside the conventional Qiskit Aer state-vector route, InferQ lowers each circuit into a tensor-network contraction and emits that contraction as a single SQL query, which is then executed on PostgreSQL, DuckDB, SQLite or Umbra. A database engine's buffer pool and spill-to-disk machinery become the memory manager for quantum simulation — which is what makes circuits too large for a 64 GB state vector still tractable.

The shape of the repository

The tree is a uv workspace with two members that are deliberately asymmetric.

src/inferq
The library and CLI. Published as a wheel. Source layout, 94 modules, 17.3k lines. Everything here must import cleanly from an installed wheel with no repository on disk.
experiments/
The research harness. Marked package = false, never published. 14.2k lines of out-of-core benchmarking, engine tuning and figure generation.
tools/
Repository maintenance: the hygiene guard that inspects built wheels, and the generator that regenerates the committed SQL reference.
docs/
Committed reference material, including one directory per generator holding the exact SQL each one lowers to under all three query modes.

The separation is enforced, not merely conventional: a hygiene check runs against the built wheel in CI and fails the build if anything from experiments/ or tools/, or any data artifact, ends up inside it.

InfiniQuantumSim is a dependency group, not an extra

The tensor-network lowering engine lives in a git repository, not on PyPI. uv sync --group infiniquantum
Graceful degradation is a tested property

The main CI job installs without that group on purpose. Every code path that touches the lowering engine degrades to a recorded failure rather than an exception, and the test suite passes with the engine absent. If you break that, CI catches it.

Quickstart

The fastest way to confirm a working environment is the end-to-end smoke test. It probes which database engines are actually reachable, generates a small circuit, runs it through the full extract-simulate-store path, and verifies what landed on disk.

Smoke test
uv run inferq smoke

# include the cloud upload leg (off by default)
uv run inferq smoke --cloud

Then generate circuits. The parallel mode is the production path.

Generate
# 5 batches of 10 circuits across 8 worker processes
uv run inferq run parallel --workers 8 --batch-size 10 --iterations 5

# one circuit, in-process, useful under a debugger
uv run inferq run single

# pick the generators by hand
uv run inferq run interactive

Or ingest a published benchmark suite instead of generating.

Ingest
uv run inferq data fetch qasmbench
uv run inferq ingest --suites qasmbench --max-qubits 20 --limit 50

Everything written lands under paths you can always print.

Where did it go
uv run inferq paths

Architecture

The three pillars

Everything the project does rests on three subsystems, and almost every module belongs to one of them. Generators produce circuits. Features measure what a circuit is. Simulation measures what a circuit costs. The pipeline is not a fourth pillar — it is the loop that drives the three in a fixed order and writes down what they produce.

That order is the design. A circuit is generated before it is measured, measured before it is run, and run before anything is written, so that a single record can carry the structure and the cost of the same circuit side by side. The whole point of the corpus is that pairing: structure on one side, cost on the other, joined by one identity.

What belongs to which pillar

PillarAnswersIts output ends up as
I · Generators What circuits should exist at all? The serialized circuit, and the composition recorded in its name
II · Features What is this circuit, structurally? Static and interaction-graph measurements — the predictors
III · Simulation What does running it actually cost, and by which route? Per-method timings, memory, state-derived measures, the lowered query and its own SQL features — the targets

Read as a machine-learning problem, pillar II produces the inputs and pillar III produces the labels; pillar I decides what the training distribution looks like. The synergy rules matter for exactly that reason — they are what keeps the corpus looking like plausible algorithm pipelines instead of uniform noise over the generator list.

The same three pillars, three entry points

Generation is not the only way through them. Three commands traverse the same pillars in the same order, differing only in where the circuit comes from and which pillars are allowed to re-run.

Entry pointPillar IPillar IIPillar III
inferq run Composes a new circuit Full pass Full sweep
inferq ingest Replaced by a published benchmark suite Full pass Full sweep
inferq rerun Skipped — reads circuits already stored Recomputed only in the dynamic-feature mode Re-run in the simulation and SQL modes

This is why the pillars are worth naming: the ingest path is not a separate pipeline, and neither is the backfill path. They are the same three stages with one stage swapped out or switched off, which is what keeps a circuit that arrived from a published suite directly comparable to one the composer invented.

Architecture

Layer map

The library is organised as a dependency stack rather than a flat set of packages. Each layer may import from the layers below it and never from the layers above. This is what keeps the import graph acyclic and what lets the test suite import every module in a fresh subprocess without tripping a cycle.

Two invariants the layers protect

Path resolution is centralised. One module resolves every filesystem location in the library, and it is the only place allowed to create a directory. Nothing touches the filesystem at import time. A hygiene rule enforces this mechanically: inside src/, walking up the tree with parents[…] is forbidden everywhere except in that one module, and hard-coding the repository's own name is forbidden outright. The result is that an installed wheel with no repository on disk behaves correctly instead of silently writing into a directory that happens to be nearby.

Configuration is a pure computation. Building the config object reads defaults and environment variables and does nothing else — no I/O, no network, no directory creation. This matters because several entry points construct it at import time, and because every worker process re-reads it per task, which is what makes environment variables a live per-task control channel.

Lazy exports

The top-level package defines a module-level __getattr__ in the style of PEP 562, memoising each resolved name back into the module globals. Twenty generator classes, the simulator and its supporting types, and the three storage entry points are all reachable as top-level attributes, but none of them — and none of Qiskit or Aer — is imported until first touched. The CLI repeats the trick one level up: the subcommand's module is imported only after argument parsing has selected it, so inferq --help never pays for Qiskit.

Architecture

Generation pipeline

The parallel pipeline is the production path. Its design is unusual in one respect worth understanding before reading the code: there is no inter-process communication beyond function arguments and return values. No queue, no pipe, no manager, no lock. The only shared object is a single integer flag used to request shutdown, and only the parent ever writes to it.

Consequences of that design

  • The pool is created once and reused for every batch. Worker start-up cost — importing Qiskit and Aer — is paid once per process, not once per batch.
  • The timeout is batch-wide, not per-task. A single pathological circuit can consume the whole budget; the remaining futures are cancelled and recorded as timeouts rather than lost.
  • Deduplication has a one-batch overlap window. Each worker is handed the union of hashes known at batch start. Two workers inside the same batch can therefore both produce the same circuit; the content-addressed write catches that at the filesystem level, where the directory creation simply fails and the second write is reported as a duplicate.
  • There is no checkpoint file. Resumability comes from three places instead: the content-addressed store itself, the duplicate cache on disk (written atomically through a temporary file and a rename), and the in-memory session union. Killing the process and restarting it resumes correctly.
  • Workers return live circuit objects. The parent holds them so that the upload leg never has to re-read what the worker just wrote.
Two things to know before tuning

The worker ceiling is 22, and the reason is not CPU count — beyond that, the cloud upload path and the per-worker Aer memory footprint become the bottleneck. And the resource monitor blocks for a full second per call while sampling CPU, and measures disk usage on the current working directory rather than on the configured store.

Architecture

Circuit to SQL

This is the mechanism that distinguishes InferQ from a conventional circuit-benchmark harness. A quantum circuit is a tensor network; contracting that network yields the output state; and a tensor contraction is a sequence of joins and sums — which is to say, it is expressible in SQL. The lowering path turns a circuit into one query and hands it to a database engine.

The K prefix is load-bearing. Everything downstream — the query mode rewriter, the CTE counters, the experiment harness's per-step statistics — identifies contraction steps by that prefix and treats every other CTE as a helper that must be carried along.

Architecture

Query modes

One lowered query, three ways to hand it to an engine. The mode is the independent variable in most of the out-of-core experiments, because it decides whether the engine gets to keep intermediate results in memory, is forced to materialise them, or is told to write each one to a real table.

The rewriter that implements this is the most carefully pinned module in the repository. It imports nothing but the regular-expression module, it extracts CTE bodies by balancing parentheses rather than by pattern-matching them, and it accepts an already-materialised query as input so that re-applying a mode is idempotent.

monolithic

Identity. The query is handed to the engine exactly as the lowering engine produced it, and the planner decides everything.

WITH t1 AS (…),
     K1 AS (…),
     K2 AS (…)
SELECT …
monolithic_materialized

Every CTE — helpers and contraction steps alike — gains a materialisation hint, forcing the engine to compute each one once into a temporary result.

WITH t1 AS MATERIALIZED (…),
     K1 AS MATERIALIZED (…),
     K2 AS MATERIALIZED (…)
SELECT …
split

Each contraction step becomes its own CREATE TABLE. Helper CTEs are repeated as a shared prefix on every statement. Returns a list of statements, not a string.

CREATE TEMP TABLE K1 AS
  WITH t1 AS (…) …;
CREATE TEMP TABLE K2 AS
  WITH t1 AS (…) …;
WITH t1 AS (…) SELECT …

Why split mode has a non-temporary variant

Split mode defaults to temporary tables, which is what you want on PostgreSQL and DuckDB. SQLite is the exception: under the compile-time setting the project's SQLite runs with, the pragma that would direct temporary storage to disk is a no-op, so temporary tables live in memory and the whole point of the mode — forcing intermediates through the storage layer — is lost. The rewriter therefore takes a flag that emits plain tables instead, and the SQLite worker passes it.

The committed SQL reference

For all 17 generators, docs/query-structures/ holds a directory containing a prose description plus the exact SQL that generator lowers to under each of the three modes. These files are generated, not hand-written, and the generator is deterministic: symbolic parameters are fixed to a fixed arithmetic progression in name-sorted order, gate names are numbered in circuit order, and the contraction path uses the plain greedy optimiser rather than the randomised one.

A dedicated CI workflow regenerates the whole tree into a temporary directory and byte-compares it against what is committed, reporting missing and stale files and failing the build on either. It runs only when the generators, the SQL modules, the doc generator itself, or the committed tree change — because unlike the main test job, it needs the git dependency installed.

Separately, the test suite reads those same 17 committed fixtures and re-derives them: applying the materialisation rewrite to the monolithic file must reproduce the materialised file byte for byte, and joining the split statements must reproduce the split file. The fixtures are both documentation and the mode rewriter's regression suite.

What the smoke test actually checks

It is worth running before anything else because it is the only command that reports on the environment rather than assuming it. It probes each database engine in turn — SQLite and DuckDB always run in-process; PostgreSQL and Umbra are contacted over their configured host and port — and builds the omission list from what it finds, so an absent engine is skipped rather than failed. It then runs the full pipeline and verifies the resulting directory on disk. Cloud upload is excluded unless explicitly requested.

Its retries change the generation seed by a fixed stride, so a retry explores different circuits instead of re-attempting the one that failed. Configuration reaches the worker children through the process environment — that is the only channel that exists.

Ingest ordering and failure handling

The ingest command sorts its work by qubit count, then source, then benchmark name, so interrupting it leaves a clean prefix of the corpus rather than a random sample. It also catches a broader class of failure than usual around the extraction and simulation steps, because one of the Rust-backed Qiskit transpiler passes raises a panic that does not derive from the ordinary exception base class; keyboard interrupts and exit requests are still re-raised.

Worker count is capped at 22

The recommended worker count is two fewer than the machine's cores, clamped to 22. The ceiling is not a CPU limit: past that point the cloud upload path and the per-worker Aer memory footprint dominate, and adding processes makes throughput worse rather than better.

Paths and data

Every location follows the same three-step precedence: an explicit environment override wins; otherwise, if the process is running from inside the repository, a directory under the repository is used; otherwise the platform's standard user directory is used.

Output is the deliberate exception: it does not live under var/ and does not follow the platform convention, because generated figures and result tables are artifacts a person goes looking for, and they should land next to where the command was run.

Detecting the repository

"Running from inside the repository" is decided by walking upward looking for a project file that belongs to InferQ specifically — either named as one of this project's own distributions, or declaring the uv workspace. A project file belonging to some unrelated project does not count. From an installed wheel the walk finds nothing and returns nothing, which is the normal case and is asserted directly in CI.

Resolving a circuit from a manifest

Manifests record both a hash and a path, and the resolver trusts the hash. Recorded paths are not portable between machines — the experiment harness runs the same manifest on a workstation and inside a container with different mounts — so the hash is used to re-derive the location, and the recorded path is only a fallback. Three on-disk layouts are probed in turn, covering the flat store, the two-character fan-out, and the directory-per-circuit form.

The registry is a hand-maintained list

There is no discovery mechanism and no registry module. The set of generators is an ordered list inside the composer, paired with a name-to-class map derived from it, and the two family memberships are separate string sets in the same file. Instantiation is defensive: any class whose constructor raises is silently dropped from the live registry rather than failing the process.

Adding a generator

Three edits in the composer, not one: the ordered class list, and both family string sets. Miss the family sets and the new generator will build fine but will never participate correctly in synergy-weighted selection.

Composition

"Hierarchical" in the composed circuit's name describes how it was selected, not how it is nested — the structure is flat. Members are placed side by side onto one register with a barrier between them, each composed starting from qubit zero across as many qubits as it needs. Parameter names are rewritten with a per-member suffix so that two copies of the same ansatz do not collide, and any parameter still free at the end is bound to a uniformly random angle.

Selection proceeds as a short weighted chain:

  1. Start from uniform weights over the live registry.
  2. Draw one generator with replacement, weighted.
  3. Damp the one just drawn so repeats are unlikely but possible.
  4. Shift the balance across families — picking a state-prep raises the algorithms and lowers the other state-preps, and the reverse for an algorithm.
  5. Apply every matching synergy rule multiplicatively, then renormalise.
  6. After the first pick, stop with a fixed probability each step; otherwise continue up to the maximum chain length.

The chain length is therefore geometric, truncated at the configured maximum. Note that the step meant to raise the stopping probability as the chain grows is written as a clamp that never actually raises it, so the stopping rate is constant in practice.

Seeding

Every parameter-sampling helper accepts a seed argument and ignores it. Seeding happens exactly once, in the composer's constructor, which seeds both the standard library's random module and NumPy's global state. This is worth knowing because it means reproducibility is a property of the composer, not of any individual sampler, and calling a sampler directly without constructing a composer gives unseeded results.

Interactive composition

A thin parsing and prompting layer sits over the composer and builds nothing itself. It accepts generator selections as indexes, inclusive ranges, or case-insensitive names, and accepts parameter overrides as JSON, as a Python literal, or as comma-separated key-value pairs. Empty input means "use the random path", which makes the interactive mode a convenient way to reach the normal generator with a seed you chose.

Feature catalogue

Feature extraction produces a single flat dictionary per circuit. Two extractors run over a shared memoisation cache and merge their output; a third, for SQL, runs later in the simulation path; dynamic features are derived from simulation results rather than from the circuit. Every individual feature computation is wrapped so that a failure writes a null instead of aborting the circuit.

One definition to be aware of

Inside the density score, the term standing in for the single-qubit gate count is actually the number of distinct gate types in the circuit, not the number of single-qubit gate instances. The value is stable and comparable across circuits, but it is not the quantity the name suggests.

Interaction-graph features

Fifteen graph measurements, all computed with rustworkx. The graph has one node per qubit and one edge per pair of qubits touched by the same multi-qubit gate; repeated interactions become edge weight rather than parallel edges. All-pairs distances are precomputed once with a weighted shortest-path pass and reused across the distance-derived measures.

Two naming notes: the minimum-cut figure is an upper bound obtained from a global minimum-cut algorithm, and the clustering coefficient is the graph's transitivity rather than the average of per-node clustering coefficients. Disabled in the current tree

A gate-dependency-graph extractor exists and would produce a critical-path length and the share of gates lying on it, but its invocation is commented out, so neither feature appears in the output today.

SQL features

The lowered query is parsed with sqlglot and reduced to a counter plus a set of join edges. The first pass walks the syntax tree counting statement types, clause types, set operations, aggregate functions, boolean connectives and predicate shapes. The classification list is ordered and stops at the first match, so a specific predicate shape is not also counted as the generic one it specialises.

The second pass recovers the join graph: explicit joins from their on-clauses, and implicit joins from where-clause predicates that span two relations, recursing into subqueries in the from-clause. Two summary counts — distinct join edges and total join occurrences — are always emitted, even when both are zero, so the feature vector keeps a stable shape.

Each resulting key is prefixed with the simulation method it describes, so the lowering engine's features are namespaced apart from anything else that might later be measured the same way.

Dynamic features

These are not computed in the feature package at all: they come out of the simulation path, from the measured properties of the resulting state. The simulator class inherits from the dynamic-feature extractor directly, which is how entropy and sparsity measurements ride along with the simulation that produced them.

Within the lowering method, seven execution backends are tracked. The omission list is resolved in three stages

Which backends run is decided by an omission list that passes through three transformations, and knowing this saves confusion when a backend you excluded still appears, or one you did not exclude does not.

  1. The configuration default omits PostgreSQL, EQC, DuckDB and Umbra — the network engines plus the one that is not executed.
  2. That list is injected into the lowering engine under a differently-named keyword argument than the one the configuration key suggests.
  3. The engine normalises aliases (underscored spellings, and DuckDB's two names) and then unconditionally appends two further backends that require servers this project never runs.

Reference

Storage and the cloud

Storage is content-addressed: a circuit's identity is a digest, and that digest is the directory name. Creating the directory is the atomic claim — the write asks for a directory that must not already exist, and the resulting collision is the deduplication signal. No lock, no check-then-write race.

On-disk layout

One circuit
<circuits root>/<full hex digest>/
├── circuit.qpy        # preferred serialization
├── circuit.pkl        # fallback if QPY refuses the circuit
├── circuit.qasm       # or circuit_info.txt, last resort
├── circuit.sql        # the lowered query, kept separate
└── meta.json          # digest, method, dimensions, mode, all features

The query lives in its own file rather than inside the metadata because split-mode output runs to tens of kilobytes and would dominate every metadata read. The metadata file carries the digest, which serialization method succeeded, the circuit's dimensions, the query mode used, and the complete feature dictionary flattened in.

Locally the layout is flat — one directory per circuit, named with the full digest. In blob storage it is different: a two-character fan-out prefix, then the digest with a file extension. The path resolver knows all the layouts and probes them in order, which is what lets the same manifest drive both.

What the digest is actually over

The identity is documented, and the metadata key is named, as the digest of the circuit's canonical QPY serialization. It is in fact the digest of the circuit's text rendering. The serialization ladder runs and its result is stored, but the hash is taken from the drawing. This is stable and collision-resistant in practice, and changing it now would re-key the entire corpus — but it is not what the name says.

Duplicate detection

Three sets are tracked and their union is what counts as known: hashes confirmed present in the remote table, hashes written locally and awaiting upload, and hashes produced in the current session. A miss is added to the session set immediately, so the same process never asks twice. The cache file is written atomically through a temporary file and a rename, so an interrupted write cannot corrupt it.

The remote check is deliberately cheap: it enumerates the metadata table selecting only the row key, because the row key is the digest. No entity bodies are transferred.

Remote schema

Two services are used on either provider: an object store for the circuit artifacts, laid out with the same fan-out, and a metadata store holding one record per circuit — a single fixed partition, the digest as the row key, and every feature as an attribute. Feature names are sanitised into valid attribute names by one shared helper — non-alphanumerics become underscores, a leading digit gets a prefix, everything is lowercased — NumPy scalars are converted to native types, and anything structured is stored as JSON text. Because the sanitiser is shared rather than reimplemented per backend, a record written on one cloud carries byte-identical attribute names on the other.

Which backend is built is a configuration question answered once, by a registry that maps a provider name to a dotted import path. Selecting one never imports the other's SDK, and importing inferq.remote imports neither. Paging is opaque on both: an Azure continuation token and a DynamoDB LastEvaluatedKey are wrapped in the same base64 cursor, so a caller resuming a scan does not know or care which cloud produced it.

Metadata updates from the backfill pipelines use a merge write, so a rerun that adds new measurements does not erase the ones already recorded.

Each provider's credentials are required together, and the credential loader collects all the missing ones before raising, so a misconfigured environment produces one message naming everything absent rather than a sequence of one-at-a-time failures.

Backfill

The rerun subsystem exists to add measurements to circuits that already exist. It is four layers — an orchestrator over folders, a folder processor, a per-circuit processor, and a checkpoint manager — and it supports three modes: re-running simulations, re-lowering to SQL, and recomputing dynamic features.

Checkpoints are append-only files of digests, one per folder, flushed immediately. A digest is recorded both when the remote merge succeeds and when the circuit is skipped by a filter, so only genuine failures are retried on the next pass. The folder processor applies memory back-pressure, pausing while system memory is above ninety per cent rather than pushing the machine into swap.

Benchmark datasets

Alongside generated circuits, InferQ ingests three published benchmark suites. Two are ordinary Python dependencies; the third is a file tree that must be fetched and verified.

The dataset registry

Fetched datasets are described by a manifest that pins far more than a URL. Each entry carries a description, homepage, licence, an upstream location, an exact commit, optional mirrors, which subdirectories to keep, how many leading path components to strip, a maximum per-file size, and a digest and byte size for every file. The single registered dataset today is QASMBench, pinned to one commit with 92 verified file entries.

Fetching never damages what you already have

The fetch procedure stages into a temporary directory, downloads with the standard library only, unpacks with the safe extraction filter explicitly enabled, and verifies the staged tree against the manifest. Only after verification passes is the existing copy removed and the staged tree moved into place. A failed or interrupted fetch leaves the previous copy intact.

Dataset commands
inferq data list
inferq data fetch qasmbench
inferq data fetch qasmbench --force   # re-fetch even if present
inferq data verify qasmbench          # full per-file digest check
inferq data verify qasmbench --quick  # sizes only

Verification reports missing and corrupt files separately, so a partially damaged tree tells you which files to worry about.

Experiments

Out-of-core harness

The out-of-core experiments test the project's central claim: that running a quantum simulation as a SQL query lets a database engine's spill machinery carry circuits that a dense state vector cannot hold. The method is to cap memory hard, at the container level, and observe what happens.

The three hypotheses

C1 — capability gap
At 31 qubits and above, a dense state vector needs more memory than the cap allows, and the Aer path fails where the relational path does not.
C2 — graceful degradation
As the cap shrinks, the relational path keeps completing rather than falling over.
C3 — paid in time
That degradation shows up as longer wall time, not as failure.
The report has no results yet

The results and interpretation sections of the experiment report are explicit placeholders. Anything results-facing must be read from the generated result tables and figures, not from that document.

Container topology

Two images are built. A PostgreSQL image adds a configuration template rendered from the memory cap at container start; a worker image pins an exact scientific stack so that measurements taken weeks apart are comparable.

The crucial detail is which container gets capped, and it differs by engine. For PostgreSQL the query executes inside the server, so the server container carries the cap and the worker gets a generous allowance over host networking. For DuckDB, SQLite and Aer the query executes inside the worker, so a single worker container carries the cap.

Making the cap real

A memory limit is only a limit if the process cannot escape it. Three settings together close the escape routes: the swap allowance is set equal to the memory allowance so swap adds nothing, swappiness is set to zero, and the temporary directory is required to be a real block device rather than a memory-backed filesystem — otherwise spilled data would count against the very cap it was meant to relieve.

The worker container runs on the host cgroup namespace with the cgroup filesystem bind-mounted read-only, and is deliberately not auto-removed on exit, so that its accounting directory survives long enough for the host-side peak to be read.

The reader handles both cgroup generations, falling back between layouts and searching for the accounting directory when the expected path is absent, with privilege escalation attempted non-interactively. The reported peak for the in-process engines is the maximum of three independent readings, which guards against any single one under-reporting.

Circuit selection

Circuits are drawn from the corpus and stratified into five bins by qubit count — under 25, 25 to 27, 28 to 29, exactly 30, and 31 or more — with a fixed number per bin. From roughly two hundred thousand candidates the main sweep uses 73 circuits, with a 25-circuit pilot for shakeout. Several purpose-built manifest builders exist alongside the stratified selector for targeted studies: QFT-only, deliberately spill-inducing, and sparse-affine families.

The manifest is line-delimited JSON. Each row carries the digest, a path, the circuit's dimensions, the peak memory previously observed and which methods produced it, and the bin assignment. The path is advisory; the digest is authoritative.

Per-engine instrumentation

Each engine is measured in whatever way gives the most honest number for it, which means they are not instrumented identically.

  • PostgreSQL — the query runs under a full analysing explain, and temporary block counts from that plan are converted to exact spill bytes. A background sampler also lists the temporary file directory several times a second, so spill that the plan does not attribute is still observed.
  • DuckDB — its own memory limit is set below the container cap with a pad and a floor, insertion-order preservation is switched off, profiling is captured as JSON, and a watchdog interrupts the connection after the timeout plus a grace period rather than letting the container be killed.
  • SQLite — the temporary directory, file-backed temporary storage, a negative cache size on both the main and temporary databases, and durability settings are all configured explicitly; in split mode it is given plain tables rather than temporary ones, for the reason described in the query-modes section.
  • Aer — given a memory ceiling derived from the cap minus a pad, so it reports its own refusal rather than being killed by the kernel.

A sweep

Default caps are 16, 8 and 4 gigabytes across PostgreSQL, DuckDB and SQLite — Aer is excluded from the default engine list and opted into explicitly, since it is the baseline being contrasted against rather than a subject. One timed run per condition with one warm-up, a thirty-minute timeout, and the page cache dropped between runs.

The reference machine is documented in the experiment report: a 64 GB desktop with a sixteen-core processor, an NVMe drive, Ubuntu 22.04 on a 5.15 kernel with both cgroup generations mounted, and Docker 24 or newer using the cgroupfs driver.

Experiments

Engine tuning

A second experiment family asks whether the relational path improves when the engine is tuned for it rather than left at defaults. Two things are compared: fixed hand-written profiles, and settings found by automatic search.

Profiles

Three static profiles — balanced, fast and spill_safe — cover the obvious trade-off between throughput and surviving a tight memory budget. A second, size-conditioned pair splits by circuit size instead; its numbers are not round because they are baked-in output from the automatic search rather than hand-chosen.

The search

Each engine gets its own search space over the settings that plausibly matter for this workload.

EngineSearched over
DuckDBmemory limit (log scale), thread count, maximum temporary directory size, insertion-order preservation
SQLitecache size (log scale), temporary storage location, memory-map size, thread count
PostgreSQLwork memory, temporary buffers, effective cache size and hash-memory multiplier (log scales), parallel gather workers, JIT, and both collapse limits

The objective is median wall time, with a design choice worth noting: a failed configuration scores a very large constant, and every additional failure adds a further large penalty on top. Reliability is therefore bought before speed — the search will not trade a working configuration for a faster one that sometimes falls over.

Result tables record the query generation cost and byte size alongside the execution measurements, so the cost of producing the query is never silently folded into the cost of running it. The schema is asserted rather than assumed, so a change to the columns fails loudly instead of producing a table that silently no longer aligns with earlier runs.

Figures

Plotting shares a small amount of infrastructure deliberately and no more: a serif font fallback chain, the target venue's exact column widths and font sizes, one fixed colour and marker per engine, byte-axis formatters, a save helper, and a correlation helper. The per-script style blocks are not shared, because the scripts target different papers and unifying them would silently change figures that have already been published. Those scripts are also excluded from the import-integrity test for the same reason — they are frozen.

Continuous integration

Three jobs, each defending something different.

  1. Test, on Python 3.12 and 3.13. Syncs the whole workspace with every extra but without the lowering engine's dependency group, then lints and runs the suite. Passing this proves the library degrades gracefully when the git dependency is absent.
  2. Package. Builds the distribution, runs the hygiene guard against the built wheel, then installs that wheel into a bare virtual environment with no repository in sight and exercises the CLI there — including asserting that repository detection correctly finds nothing.
  3. Query docs. Runs only when the generators, the SQL modules, the doc generator or the committed SQL tree change. Installs the lowering engine, regenerates everything, and byte-compares against what is committed.
